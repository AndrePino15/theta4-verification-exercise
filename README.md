# THETA 4 - Formal Verification of FIFO Buffer
This repo is the 4th design exercise of the Programming and Simulation of Electronic Systems Module of Year 2, University of Southampton EEE. Its task is to verify a given design of a FIFO Buffer. The student decides what to check and how to do it, and has to build a testbench implementing the test and write a report describing, exlaining and justifying all the tests perfromed by the testbench(es).

## Given Instrucitons

### Background
In many respects, verification is a more difficult task than design. Verification can take longer and good verification engineers are rare. Verification needs to demonstrate that a design meets its specification, but also to understand how a design behaves with unexpected inputs. Therefore, a simple simulation that shows one example of correct behaviour is not enough. Equally, a screen dump of a simulation is not sufficient evidence that a design meets its specification.

Ideally, the design and verification should be done by different teams, so that the verification is thorough and unbiased. Therefore, you are asked to verify a design that you have not previously seen. This design may contain errors, but the aim of this exercise is not to fix any such errors, but, instead, to demonstrate that you have thoroughly simulated the entire design.

### Task
In the simplest sense, you have to develop a testbench. First, however, you have to decide what the testbench will do. You might decide to check that:

- Every possible input and combination of inputs is simulated;
- Every possible output is simulated;
- Every line of code is executed;
- Every branch (if, case) is tested.

All of these can be expressed in terms of coverage. Some of these metrics are easier to achieve than others. You may also need to change design parameters to test different configurations.
Testbenches can be written in different ways:

- A “monolithic” testbench that does everything;
- A structured testbench that reuses code;
- An established methodology, such as UVM, cocotb, or AVL.

(Unless you have used UVM, previously, you are strongly advised not to try that approach!)
Testbenches can be written in SystemVerilog or Python (cocotb). You can use ModelSim/QuestaSim, or an open-source tool such as Verilator. (Again, unless you have previous experience, you are strongly advised to use SystemVerilog and ModelSim.)

You are free to use any or none of the techniques that have been described in lectures, including SystemVerilog Assertions, Coverpoints, Constrained Random Verification, etc. Your testbench should print results in the form of data about the quality (coverage) of your simulation(s).

## Specification of Design Under Verification
The design to be verified is a parameterizable FIFO (First-In, First-Out buffer). The design is clocked by a single, positive clock edge. There is a synchronous, active low reset that initialises the pointers in the FIFO, but which does not initialise the contents of the FIFO buffer.

The FIFO is parameterized in terms of its bit-width and depth. There are two thresholds that will assert outputs when the FIFO is almost full or almost empty. The FIFO has two active high control signals: write enable (we) and read enable (re) that allow data to be written into and read from the buffer. There is a write data (wrdata) input that holds new data to be written to the FIFO. Similarly, there is read data (rddata) output that returns data from the FIFO. Data should be read out in exactly the same sequence that it was written. The FIFO may be written to and read from in the same clock cycle.

There are 4 status flags: full, empty, almost_full, and almost_empty. When full is high, data cannot be written to the FIFO. When empty is high, the data read from the FIFO is not defined.

When the number of FIFO entries is less than the almost empty threshold, the almost_empty flag is high. When the number of entries is greater than the FIFO depth minus the almost high threshold, the almost_full flag is high.

The addresses at which data is read or written are not visible outside the FIFO. Hence, the FIFO addresses should “wrap around” transparently.
